  Is flue a harness itself? — Yes, but the word is hiding three things

  That's exactly why it feels mysterious: "harness" is used for three different
  layers, and nothing tells you they're different.

  1. The LLM loop — read → call a tool → observe → repeat. This is the actual
  agentic engine, and it isn't even Flue's code: it's a dependency,
  pi-agent-core. Flue wraps it. (You can watch the wrapping happen —
  packages/runtime/src/session.ts:679 does this.harness = new Agent(...),
  importing Agent from pi-agent-core.)
  2. Flue's Harness object — the thing you get back from const harness = await
  init(agent). It's a handle to sessions, filesystem, sandbox, and tools. Not
  the loop — the programmable boundary around it.
  3. Flue the framework — "The Agent Harness Framework." It supplies the harness
  half of the equation agent = model + harness.

  So the precise answer: Flue is a framework for building agent harnesses —
  "Next.js, but for agents." Next.js doesn't reinvent HTTP; Flue doesn't
  reinvent the LLM loop. It gives you everything around it (sessions, tools,
  skills, filesystem, sandbox, persistence, build pipeline) so a model becomes
  an autonomous agent you can deploy headlessly to Node, Cloudflare, or CI.

  What it actually does, in one breath: you write agents (addressable,
  persistent, reached by URL) and workflows (bounded jobs with run history) as
  TypeScript + Markdown; flue build compiles them into a deployable server; at
  runtime a model runs inside the harness with a sandbox (in-memory by default —
  that's the "no container" headline) to do real work without a human in the
  loop.

> Can we say flu is a harness compiler?                                         
● Honest answer: it's a useful half-truth — accurate about one real thing,
  misleading as a whole-framework label. Let me separate the two.

  Where "harness compiler" is genuinely right

  There is a real compile step. flue build (in @flue/cli) runs a Vite build
  graph that takes your authored sources — agents/*.ts, workflows/*.ts,
  AGENTS.md, .agents/skills/* — and emits a deployable server artifact (./dist:
  a single Node .mjs, or a Cloudflare Worker + Durable Objects). That step does
  compiler-ish work: it validates your static skill imports, packages each
  SKILL.md and its permitted supporting files, rejects files that look like
  secrets, and bundles everything for a chosen --target. So "Flue compiles your
  project" is a true sentence.

  Where it misleads

  The phrase mislabels the whole because the harness isn't what gets compiled,
  and a harness isn't what comes out.

  - The object of compilation is your project (agents + workflows + Markdown
  context), not a harness.
  - The output is a server, not a harness. The harness is constructed later, at
  runtime, by init(agent) → Harness → Session. The compiler emits something that
  manufactures harnesses on demand; it doesn't emit a harness.
  - Most of Flue's value lives at runtime, not in the build: sessions, message
  persistence (Durable Objects / in-memory), the sandbox, routing, the
  pi-agent-core loop. "Compiler" quietly throws all of that away.

  So the strict reading is: flue build compiles your agents into a
  harness-serving server. Neither end of that is a harness — which is why
  "harness compiler" doesn't quite land.

  The sharper label

  Flue is a harness framework with a compiler in it — exactly the Astro/Next.js
  shape the README invokes. Nobody calls Next.js a "page compiler," even though
  next build absolutely compiles pages into a server; the compiler is one part
  of a framework that's mostly runtime. Same here.

  If you want a one-liner that keeps the compiler insight without overclaiming:

  ▎ Flue compiles declarative agent definitions (TypeScript config + Markdown
  ▎ context) into a deployable server that constructs harnesses at runtime.

  That credits the build step and names what actually comes out.

  session.prompt(), turn-by-turn

  The crucial thing to hold onto: "turn" means two nested things, and prompt()
  lives in the outer one.

  - Operation = your one session.prompt() call (Flue's code).
  - Turn = one LLM round-trip (provider HTTP call) inside pi-agent-core. One
  Operation drives 1…N Turns.

  Here's the whole path, with file:line anchors in
  packages/runtime/src/session.ts:

  A. Setup (before any model call)

  1. prompt(text, options) → createCallHandle(signal, …) wraps the work in an
  abortable handle (:839). Your signal / .abort() plugs in here.
  2. runOperation('prompt', …) (:1486) takes the session's exclusive lock — only
  one prompt/skill/task/shell runs at a time per session — and wires abort to
  harness.abort() (:1502).
  3. buildPromptText(text, schema) (:843) — if you passed a result: schema, the
  prompt is augmented to tell the model to return data via a finish tool.
  4. runPromptCall(…) (:2085): if there's a schema, createResultTools(schema)
  mints two synthetic tools — finish (success; params = your valibot schema) and
  give_up (typed failure).
  5. withCallOverrides(…) (:1258) snapshots harness state, then for this call
  only resolves the model, thinking level, and assembles the toolset:
  [...builtin (read/glob/grep/bash/task), ...your defineTool tools, ...result
  tools] and assigns it to harness.state.tools. A finally restores the old state
  afterward — that's why per-call overrides don't leak.

  harness here is the pi-agent-core Agent (layer 1), stored at :679.

  B. The turn loop — runModelTurnWithRecovery (:1666)

  while (true):
    beforeLength = harness.state.messages.length
    await start()                  // → harness.prompt(text, images)  ← kicks
  pi-agent-core
    await harness.waitForIdle()    // engine runs ALL its internal Turns until
  done
    await syncHarnessMessagesSince(beforeLength, source)   // append to history
  + persist
    latest = last message
    if not assistant            → return
    if context overflow         → compact, then start = harness.continue();
  retry
    if retryable model error    → backoff, then start = harness.continue();
  retry
    else checkCompaction();       return

  Note what this outer loop actually does: it is recovery only
  (overflow→compaction, transient-error backoff). The normal read→tool→observe
  iteration is not here — it happens inside harness.prompt()/waitForIdle(), in
  pi-agent-core.

  C. Inside one harness.prompt() → the Turns (observed via the subscribe handler
  :695 and emitTurnRequestAndStream :612)

  For each Turn the engine runs:
  1. turn_start → Flue assigns an activeTurnId, emits turn_start (:700).
  2. emitTurnRequestAndStream (the streamFn, :612) emits a turn_request event
  carrying the full input (systemPrompt, messages, tools), then calls
  streamSimple(model, context, options) — this is the literal provider HTTP
  streaming call (pi-ai).
  3. Streaming deltas come back as message_update → re-emitted as text_delta,
  thinking_start/delta/end (:708).
  4. If the assistant message contains tool calls, the engine (configured
  toolExecution: 'parallel', :690) fires tool_execution_start and runs each
  tool's execute(id, params, signal) — e.g. bash hits the sandbox via env.exec.
  Results are appended to the message list.
  5. The engine loops back to step 1 with tool results in context — another
  Turn, another streamSimple call — until the model emits a final assistant
  message with no tool calls. Then it goes idle and waitForIdle() resolves.

  So a single prompt() that involves the model running three bash commands is
  roughly 4 Turns (3 tool-calling round-trips + 1 final answer), all inside one
  start().

  D. Persistence & return

  - After the engine idles, syncHarnessMessagesSince (:1632) slices the new
  messages, appends them to SessionHistory, and calls save() (:1639) → writes to
  the SessionStore (in-memory on Node by default; Durable Object storage on
  Cloudflare). Persistence happens once per idle cycle, not per Turn.
  - No-schema path: returns { text: getAssistantText(), usage:
  aggregateUsageSince(beforeLeafId), model } (:2136).
  - Schema path: runWithResultTools (:2156) inspects the outcome — finished →
  returns validated data; gave_up → throws ResultUnavailableError; pending
  (model replied but never called finish) → sends a nudge follow-up and loops,
  up to MAX_FOLLOWUPS = 32 (:2165).

  pi-agent-core's — exactly the layer-1/layer-2 split from FLUE-DEMYSTIFIED.md.
